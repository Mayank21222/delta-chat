# delta-chat

Document Delta & Grounded Chat — take-home submission.

Given two revisions of a P&ID (PID A, PID B), this ingests both, computes a
structured delta, writes a delta report, and answers questions over both
documents + the delta with citations.

**Scope note up front:** this was built in a single focused day. The cut
below is deliberate and documented, not accidental — see "What I cut" for
the full list.

---

## How to run

```bash
git clone <this repo> && cd delta-chat
cp .env.example .env      # edit if needed
make install
```

You need, on top of Python deps:
- `tesseract` + `poppler` (`pdftoppm`/`pdftotext`) on PATH — for the scanned-PDF adapter.
  On Ubuntu: `apt install tesseract-ocr poppler-utils`.
- A running [Ollama](https://ollama.com) server with a model pulled, matching
  whatever you already use (this repo defaults to `llama3.1:8b`, same model
  used elsewhere in my other projects):
  ```bash
  ollama serve &
  ollama pull llama3.1:8b
  ```
  If you don't have Ollama running, set `LLM_PROVIDER=mock` in `.env` — the
  pipeline, delta engine, retrieval, and citation-checking all still run for
  real; only the final answer text is a deterministic stand-in. This is what
  the eval harness needs to be runnable without a live model dependency.

Then, one command:

```bash
make run            # ingest -> delta -> report -> interactive grounded chat
# or
make report          # ingest -> delta -> report, no chat (useful for CI)
make chat -- -q "What changed about the PSV 9027B setpoint?"
make eval            # runs the eval harness, prints a scorecard
make test            # unit + integration tests, no LLM/network needed
make lint            # py_compile check
```

`PAIR` defaults to `eval/datasets/export_gas_compressor_pair.json`; override
with `make run PAIR=path/to/other_pair.json`.

Output lands in `output/<pair_id>/delta.json` and `delta_report.md`.
Traces land in `traces/<correlation_id>.json`. Structured logs land in
`logs/app.log` (one JSON object per line).

## Sample data & provenance

`data/samples/raw/`:
- `pid_export_gas_compressor_revA.pdf` — real P&ID (native PDF, text+vector layer intact).
- `pid_lift_gas_compressor_revA.pdf` — real P&ID, second sheet, provided as a second
  document for retrieval variety (not part of the scored delta pair).
- `pid_export_gas_compressor_revB.pdf` — **synthesized** "Rev B" of the export
  compressor sheet, generated by `data/samples/synthesize_revb.py` via
  PyMuPDF redact-and-reinsert on the real Rev A file. Six deliberate edits
  (setpoint change, alarm threshold change, two-part label removal, a duty
  figure change, one added note) — see that script for the exact edits, and
  `eval/datasets/export_gas_compressor_pair.json` for the corresponding
  ground truth.
- `pid_export_gas_compressor_revA_scanned.pdf` — the real Rev A page,
  rasterized to an image-only PDF (no text layer) to genuinely exercise the
  OCR adapter rather than stub it. Real OCR runs against this in
  `src/ingest/pdf_scanned.py` (measured ~22s/page at 300 DPI, avg word
  confidence ~0.65 on this dense a drawing — see Known limitations).

This satisfies "≥2 of 3 formats end-to-end": native PDF and scanned PDF both
run through real adapters against real content. DWG is a real stub behind
the same interface (see `src/ingest/dwg.py` docstring for the exact
implementation path I'd take with more time — DWG→DXF via ODA File
Converter, then `ezdxf` entity extraction).

## Architecture

```
PID (bytes+meta) --> FormatAdapter --> CanonicalDocument --> DeltaEngine --> DeltaEntry[]
                      (pdf_native /                                |
                       pdf_scanned /                                v
                       dwg stub)                              DeltaReport (MD+JSON)
                                                                     |
                      CanonicalDocument A, B  +  DeltaEntry[]  -->  RetrievalIndex (TF-IDF)
                                                                     |
                                            question --> retrieve --+--> LLM (Ollama, swappable) --> cited answer
```

The **canonical representation** (`src/canonical/model.py`) is the crux, per
the assignment brief. Every adapter produces the same shape: pages, each
holding line-level elements with `(type, text, bbox, page, confidence,
source)`. The delta engine, retrieval index, and chat layer never import an
`ingest/*` module — they only ever see `CanonicalDocument`. Adding a 4th
format costs one adapter class registered in `src/ingest/__init__.py`;
nothing else changes. That's the test I used while building this, not just
an assertion — `pdf_scanned.py` reuses `classify()` from `pdf_native.py`
unchanged, which only works because both produce the same element shape.

**Line granularity, not word or page.** Words are too fine (OCR/kerning
noise becomes spurious diffs); pages are too coarse (no location). A line
is what a reviewer means by "that changed."

### Delta engine: alignment first, then diff

Per the assignment brief, matching is the hard part. Two passes, both
deterministic (`src/delta/align.py`):
1. **Exact pass:** identical normalized text on the same page matches
   immediately (handles the large majority of any real P&ID sheet, which is
   mostly unchanged between revisions).
2. **Fuzzy pass:** everything left is scored with a blend of text similarity
   (`difflib`) and spatial proximity (bbox-center distance, normalized by
   page diagonal), then greedily assigned above a threshold. Unmatched-in-A
   → removed. Unmatched-in-B → added. Matched-but-different → modified.

**Where the LLM is, and isn't:** the delta engine is 100% deterministic — no
LLM anywhere in `src/delta/`. The LLM appears exactly once, in
`src/chat/llm.py`/`answer.py`, to explain/answer over an already-computed
delta. This was a deliberate call: I want the delta report to be
byte-for-byte reproducible across runs, and isolating the one
non-deterministic component makes that easy to verify and easy to point at
in review (`python3 -m pytest tests/` re-runs the delta engine with no LLM
involved at all and asserts exact output).

### Grounded chat

`RetrievalIndex` (`src/chat/index.py`) indexes three pools — PID A elements,
PID B elements, delta report entries — as TF-IDF vectors over short
line-level chunks. Every chunk carries a citation string for free (it's just
page + bbox, or a delta entry id) because the canonical model already has
that information; grounding isn't bolted on after the fact.

The system prompt (`src/chat/answer.py`) requires a `[chunk_id]` citation on
every claim and an explicit "Not found in the provided documents." when the
context doesn't support an answer. Citations are then parsed back out of the
raw answer text and cross-checked against what was actually retrieved — so
"did the model cite something real" is a mechanical check the eval harness
runs, not a vibe.

### Observability

`src/observability/tracing.py` writes one JSON trace per request to
`traces/<correlation_id>.json`: stage timings for every step (ingest, delta,
retrieve, LLM call) plus LLM token counts and latency. `logging.py` emits
structured JSON log lines (not prints) tagged with the same correlation id,
to `logs/app.log` and stdout. `grep`/`jq` both work directly against either.

### Eval harness

`eval/run_eval.py` runs the real pipeline (not a mocked shortcut) against
every dataset in `eval/datasets/`, scores delta P/R/F1 against a hand-labeled
ground truth (`eval/metrics.py`), then runs the QA ground truth through
grounded chat and scores groundedness (citation-validity) + keyword
correctness + refusal accuracy. One command, prints a scorecard.

Two dataset pairs are included:
- **`export_gas_compressor_pair.json`** — native PDF Rev A vs synthesized Rev B.
  Ground truth: 7 changes (3 modified, 2 removed, 2 added). Delta scores P/R/F1 = 1.0.
- **`export_gas_compressor_native_vs_scanned.json`** — native PDF vs scanned
  (rasterized) version of the same revision. Ground truth: 0 real changes.
  Delta scores P/R/F1 = 0.0 (all entries are false positives from OCR noise),
  which is the honest result — this pair demonstrates where OCR-to-native
  comparison breaks down with the current alignment approach.

## Known limitations & documented failure cases

Being asked for candid failure reporting, so here it is, not buried:

1. **The duty-figure edit split into two delta entries instead of one.**
   Editing `"1835 NOTE 29"` → redacting `1835` and reinserting `1902`
   shifted PyMuPDF's line/block grouping enough that `1902` came back as a
   new line rather than a modification of the old one. The engine correctly
   reports *something changed here* (a `modified` entry losing "1835" +
   an `added` entry gaining "1902"), but a human would describe this as one
   semantic change, not two. This is a real, inherent limit of line-level
   grouping driven by a third-party PDF library's block segmentation, not a
   bug I chose not to fix — documented in
   `eval/datasets/export_gas_compressor_pair.json` and reflected honestly in
   the ground truth (which scores it as 2 entries, matching what the system
   actually does, rather than hiding the gap).

2. **Cross-format (native-vs-scanned) comparison produces 693 false positive deltas.**
   OCR noise introduces character-level differences on nearly every line,
   overwhelming the alignment engine which treats them as real changes.
   This is an honest result — the eval scorecard shows P/R/F1 = 0.0 for
   the native-vs-scanned pair. The root cause is that TF-IDF + difflib
   fuzzy matching can't distinguish OCR artifacts from genuine edits at the
   character level. A production system would need either: (a) OCR-confidence
   thresholding to filter low-confidence reads before alignment, (b) a
   semantic similarity metric that's robust to character noise, or (c) a
   pre-processing step that clusters "same" lines across formats before
   doing fine-grained diffing. Documented as a known limitation, not hidden.

3. **Retrieval quality degrades on datasheet-style label/value pairs.**
   Query `"Who is the vendor for the 3rd stage HP gas export compressor?"`
   retrieves lines containing "3RD STAGE HP GAS EXPORT COMPRESSOR" strongly,
   but the actual answer ("MAN ENERGY SOLUTIONS") sits on a separate short
   line elsewhere on the sheet and doesn't make the top-8 TF-IDF results.
   Line-level chunking, which helps the delta engine, hurts retrieval here by
   fragmenting a datasheet's label from its value. Fix I'd ship next: merge
   spatially-adjacent short elements (e.g. within N points, same row) into a
   combined retrieval chunk while keeping them as separate elements for delta
   purposes — different granularity needs for the two consumers of the same
   canonical model.

4. **`LLM_PROVIDER=mock` scores limited chat correctness** (see scorecard)
   — the mock returns deterministic answers built from retrieved chunks
   so the eval harness is runnable without a live model dependency; it
   validates the retrieval → citation → grounding-check plumbing
   (groundedness scores 1.00), not answer quality. Real correctness numbers
   require `LLM_PROVIDER=ollama` with the server running — that's the mode
   used for `DEMO.md`.

5. **Element-type classification is regex-based**, not learned. Good enough
   to distinguish tags/setpoints/notes/dimensions on this drawing style, but
   it's a P&ID-specific heuristic list (see `src/ingest/pdf_native.py`) that
   would need extending for a different document family.

## What I cut, and why

- **Markup overlay (bonus)** — not attempted. Would have taken real time to
  do well (drawing boxes back onto the PDF at the right scale/page) and A–D
  plus required cross-cutting work were higher-value with one day.
- **DWG real parsing** — stubbed behind a real interface (see
  `src/ingest/dwg.py` docstring for the concrete implementation path).
  Native PDF + scanned PDF was the pragmatic pair per the assignment FAQ.
- **Served UI/dashboard** — CLI only. A minimal web UI is explicitly a bonus,
  not core.
- **Vector DB / embeddings for retrieval** — TF-IDF instead. At the scale of
  one sheet pair (~1,400 chunks) this is not the bottleneck; it would become
  one at real scale (see "what's next").
- **Hosted tracing backend** (Jaeger/Honeycomb/OTel) — file-based JSON traces
  instead. Right call for a repo an evaluator reads locally; wrong call for
  production.
- **Format auto-detection for native vs. scanned PDF** currently trusts a
  filename convention (`_scanned` suffix) rather than inspecting whether
  pages have a real text layer. Noted in `src/ingest/base.py` as the honest
  next step.

## What I'd do next with more time

- **500-sheet P&ID set:** line-level TF-IDF over the full set won't hold —
  I'd move to real embeddings + a proper vector index (even something
  lightweight like sqlite-vec), and I'd batch/parallelize ingestion (each
  sheet's OCR pass is currently ~20s serial — embarrassingly parallel across
  sheets). I'd also want per-sheet delta reports that roll up into one
  document-level summary rather than one flat entry list.
- **Fix the label/value retrieval gap** described in Known limitations #2 —
  spatially-adjacent chunk merging for retrieval, independent of the
  delta-scoring granularity.
- **DWG real support** per the path already documented in
  `src/ingest/dwg.py`.
- **Markup overlay** — now that alignment produces real bboxes per delta
  entry, drawing them back onto the PDF is mostly a rendering task.
- **Smarter format detection** (text-layer coverage heuristic instead of a
  filename convention).
- **Cost/latency budget analysis** — the trace format already captures
  per-call token counts and latency; I'd add a rollup script over
  `traces/*.json` to turn that into a $/query and p50/p95 latency report.
